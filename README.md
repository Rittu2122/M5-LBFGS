# A Limited-Memory M5 Quasi-Newton Method

This repository contains the Python implementation and numerical experiments for the manuscript **“A Limited-Memory M5 Quasi-Newton Method”** by Milan De and Manoj Kumar.

The proposed method, **M5–LBFGS**, combines the three-stage M5 method for nonlinear equations with an L-BFGS approximation of the inverse Hessian. The same inverse-Hessian approximation is used in all three stages. A common damping parameter scales the three-stage construction, and backtracking accepts a trial step when it satisfies both a sufficient-descent condition and the Armijo condition.

The notebook compares M5–LBFGS with two L-BFGS implementations:

- **L-BFGS (Wolfe):** the standard L-BFGS method with strong Wolfe conditions, using SciPy's Moré–Thuente line search.
- **L-BFGS (Armijo):** the standard L-BFGS direction with Armijo backtracking. This is a control method using the same backtracking factor and curvature-pair retention rule as M5–LBFGS.

The convergence analysis establishes finite termination of backtracking, sufficient decrease, global convergence, and R-linear convergence under the assumptions stated in the manuscript. In particular, the Hessian is assumed to have uniform positive lower and upper bounds on the initial level set. The CUTEst experiments also include nonconvex problems; the numerical results on those problems are empirical and are not covered by the stated convergence theory.

## Test problems

The experiments use unconstrained, twice continuously differentiable problems from the [CUTEst collection](https://github.com/ralna/CUTEst), accessed through [PyCUTEst](https://github.com/jfowkes/pycutest). Each problem uses its standard starting point. The two test sets are constructed and analysed separately because many problem names occur in both sets at different dimensions.

| Test set | Dimension range | Dimension selection | Number of problems | Result file |
|---|---:|---|---:|---|
| Test set I (`main`) | `1000 ≤ n ≤ 2996` | Smallest available dimension in this range | 98 | `results_main.csv` |
| Test set II (`large`) | `5000 ≤ n ≤ 10000` | Largest available dimension in this range | 66 | `results_large.csv` |

Four problems are excluded where they occur in the candidate sets:

- `FLETCBV2` and `MOREBV`: the standard starting point already satisfies the stopping test because the objective is scaled by the square of the mesh size.
- `FLETCBV3` and `INDEF`: the objective is unbounded below.

The test-set definitions, including the CUTEst size parameters used to obtain the dimensions, are listed explicitly in Part 3 of the notebook.

## Methods and experimental settings

All three methods use the same default L-BFGS memory size, `m = 5`, and the same stopping test:

\[
\|g_k\| < 10^{-5}\max\{1,\|x_k\|\},
\]

following Liu and Nocedal (1989, equation (2.8)). The maximum iteration count is 50,000 for every method, problem, and memory size.

| Setting | Value used in the notebook |
|---|---|
| Default L-BFGS memory | `m = 5` |
| Initial inverse-Hessian scaling before any pair is stored | `γ_init = 1 / ‖g_0‖` |
| Initial scaling after a pair is available | `γ_k = (sᵀr) / (rᵀr)` |
| Stopping tolerance | `TOL = 10⁻⁵` |
| Maximum iterations | `MAX_ITER = 50000` |
| Armijo constant | `C1 = 10⁻⁴` |
| M5 sufficient-descent constant | `C_D = 10⁻⁴` |
| Strong Wolfe curvature constant | `C2 = 0.9` |
| Backtracking factor | `RHO = 0.5` |
| Maximum backtracking trials | `MAX_BACKTRACK = 60` |
| Curvature-pair threshold for the Armijo methods | `sᵀr ≥ 10⁻¹⁰ sᵀs` |
| Timing repetitions | `REPEATS = 3` total runs for each initially converged problem–method pair |
| BLAS/OpenMP threads | One thread (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, and `MKL_NUM_THREADS` are set to `1`) |

**L-BFGS (Wolfe)** uses the strong Wolfe conditions with `c1 = 10⁻⁴` and `c2 = 0.9`, starting from a unit step. Every correction pair is stored.

**L-BFGS (Armijo)** uses the search direction `−H_k g_k` and Armijo backtracking from `α = 1`, with factor `β = 1/2` and at most 60 trial values. A correction pair is stored only if it satisfies the curvature-pair threshold above.

**M5–LBFGS** recomputes the complete three-stage construction for each trial value of `α`. A trial is accepted only when both the sufficient-descent condition

\[
-g_k^T d_k(\alpha) \ge C_D\,\alpha\,g_k^T H_k g_k
\]

and the Armijo condition hold. It uses the same curvature-pair retention threshold as L-BFGS (Armijo).

A run is unsuccessful if it does not satisfy the stopping test within 50,000 iterations, the Wolfe line search fails, or all 60 backtracking trial values are rejected. The solver checks the stopping test at the start of each iteration and again after the final update at the iteration limit. Thus, an iterate that satisfies the stopping test immediately after the 50,000th update is classified as converged.

### Timing and evaluation counts

The notebook counts all gradient evaluations, including gradients at the intermediate M5 points and at rejected trial values. Function evaluations are also counted.

CPU time is measured using process time. For a problem–method pair whose initial run converges, the solver is run three times in total (the initial run plus two repeats). The median of the timings from runs that converge is stored. If the initial run does not converge, it is run once. A repeat that does not converge is excluded from the timing median. CPU timings may vary with the Colab machine and system load; iteration counts, gradient-evaluation counts, convergence classifications, and final values are determined by the implementation and inputs.

## Running the notebook

The notebook is designed for **Google Colab with a CPU runtime**; no GPU is required.

1. Upload or open `M5LBFGS_CUTEst_final(4).ipynb` in [Google Colab](https://colab.research.google.com/).
2. Select a CPU runtime and run the notebook from top to bottom using **Runtime → Run all**.
3. Part 1 installs the required CUTEst/PyCUTEst build tools and libraries. It installs `gfortran`, `meson`, `ninja`, `pycutest`, and `jinja2`, and clones/builds the SIFDecode, CUTEst, and SIF repositories when needed.
4. Part 2 mounts Google Drive by default and creates the result directory:

   `MyDrive/M5LBFGS_CUTEst_results_repeat_all_converged`

   It also records the software versions and machine information in `environment.txt`.
5. Part 6 runs the three methods on both test sets. The raw results are saved as `results_main.csv` and `results_large.csv`. Results are written after each problem has been processed.
6. If a Colab session disconnects, reconnect to the **same Google Drive account and result folder**, then run the notebook again. Completed problem–method results already present in the CSV files are skipped, and missing runs are continued.
7. Parts 7–10 load the results and generate the per-problem tables, summary tables, failure tables, and performance profiles.
8. Part 12 runs the memory-size study on Test set I for `m = 3, 10, 20`; the `m = 5` results are taken from the main experiment.
9. Part 13 compares the notebook's L-BFGS (Wolfe) implementation with SciPy's L-BFGS-B implementation on the Test set I problems solved by L-BFGS (Wolfe). It compares iteration counts, not CPU times.
10. Part 19 packages the available result files into `M5LBFGS_CUTEst_results.zip` and downloads the archive. Part 11 also provides a ZIP download after the main experiment and performance-profile outputs have been generated; Part 19 is the final download step after the memory and SciPy checks.

### Reusing saved results and starting a fresh experiment

By default, `USE_DRIVE = True`, and the notebook saves results in the Google Drive folder specified by `DRIVE_FOLDER` in Part 2. To resume an interrupted experiment, keep the same folder. To perform a **fresh experiment**, change `DRIVE_FOLDER` to a new folder name before running Part 2, so that old CSV files are not reused.

If Google Drive is unavailable, the code falls back to a local `results` directory under the CUTEst working directory. Local Colab files do not persist after the runtime is lost.

The complete experiments can take several hours, depending on the Colab runtime and the CUTEst problems being processed.

## Summary of the main numerical results

The currently reported main-experiment results are summarized below. The geometric-mean ratios are computed over the problems solved by all three methods. For the iteration ratio, a value below 1 favours M5–LBFGS; for gradient evaluations and CPU time, a value above 1 indicates greater cost for M5–LBFGS.

| Measure | Test set I (98 problems) | Test set II (66 problems) |
|---|---:|---:|
| Problems solved: L-BFGS (Wolfe) / L-BFGS (Armijo) / M5–LBFGS | 84 / 87 / **89** | 60 / 61 / **63** |
| Geometric mean iteration ratio: M5–LBFGS / L-BFGS (Wolfe) | **0.56** | **0.62** |
| Geometric mean gradient-evaluation ratio: M5–LBFGS / L-BFGS (Wolfe) | 2.16 | 2.40 |
| Geometric mean CPU-time ratio: M5–LBFGS / L-BFGS (Wolfe) | 1.71 | 1.97 |

M5–LBFGS solves more problems than either L-BFGS implementation in both test sets and requires fewer iterations on most commonly solved problems. However, its three-stage construction requires more gradient evaluations, and the reduction in iteration count does not generally translate into lower CPU time. These results support the interpretation of M5–LBFGS as an iteration-efficient method whose practical benefit depends on the relative importance of iteration count, gradient evaluations, and robustness.
